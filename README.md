# Servo Tester

Настольное приложение и прошивка ESP32 для настройки и проверки сервопривода
**Feetech STS3215**, подключённого через плату **Waveshare Servo Driver with
ESP32** (SKU 21593).

Приложение открывает Serial-порт, читает и записывает конфигурацию, запускает
поиск механического нуля, управляет приводом в позиционном режиме и в режиме
непрерывного вращения, показывает телеметрию и строит графики в реальном
времени. Работать можно и **без платы**: в списке портов есть демо-режим, где
отвечает встроенный эмулятор.

Python 3.10 и новее, PySide6, pyqtgraph, pyserial. Прошивка на Arduino
Framework через PlatformIO.

## Быстрый старт

```bash
python3 -m venv venv
source venv/bin/activate          # Windows: venv\Scripts\activate
pip install -r requirements.txt
python -m desctop_app
```

Плата не нужна: выберите в списке портов пункт **«Демо, работа без платы»** и
нажмите «Подключиться». Отвечать будет эмулятор, который реализует тот же
протокол, что и прошивка.

### Если порт не открывается

- **Linux:** пользователь должен состоять в группе `dialout`, иначе
  `/dev/ttyUSB0` не откроется. `sudo usermod -aG dialout $USER`, затем
  перелогиниться.
- **macOS:** порт называется `/dev/cu.usbserial-*`. Брать нужно `cu.*`, а не
  `tty.*`.
- **Windows:** порт вида `COM3`, может понадобиться драйвер CH340 или CP210x.

Порты без `vid` (на Linux это `/dev/ttyS0` и далее) создаются ядром всегда,
даже если физически их нет. USB-устройства в списке идут первыми.

## Прошивка ESP32

**Из исходников**, если установлен PlatformIO:

```bash
pio run -d esp32 -t upload
```

**Готовым бинарником**, без исходников и тулчейна:

```bash
pip install esptool
esptool.py --chip esp32 --port /dev/ttyUSB0 --baud 921600 \
    write_flash 0x0 esp32/firmware/servo-tester-esp32-v0.3.0.bin
```

Файл собран склейкой загрузчика, таблицы разделов и прошивки, поэтому
заливается одной командой с адреса `0x0`. Кнопки BOOT и EN зажимать не надо:
на плате автоматическая схема загрузки. Версия прошивки возвращается в ответе
на команду `ping`, по ней можно убедиться, что залита именно эта сборка.

## Подключение оборудования

```
ПК --USB Type-C--> плата ESP32 --3-pin шлейф--> STS3215
                      ^
                 DC 6..12 В
```

- Сервопривод втыкается в **любой из двух** трёхпиновых разъёмов платы, они
  соединены параллельно.
- **Питание через разъём DC 5.5x2.1 мм, 6..12 В.** Плата подаёт это напряжение
  **на сервопривод напрямую, без преобразования**, поэтому его выбирают под
  конкретную модификацию STS3215: 12 В или 7.4 В. Подача 12 В на
  семивольтовую сборку выведет привод из строя.
- **Ток блока питания от 3 А:** заводской ток защиты сервопривода составляет
  500 единиц по 6.5 мА, то есть 3250 мА.
- **USB питает только логику ESP32.** Без внешнего питания плата ответит на
  `ping`, но поле `servo` будет `false`, а привод не двинется.
- Прошивать можно без блока питания.
- Прошивка ожидает **ID 1** и **скорость шины 1 Мбод**, то есть заводские
  значения сервопривода. Если их меняли другой утилитой, нужно вернуть.

## Архитектура

```
        интерфейс (PySide6)          desctop_app/ui/
               |
         Client: команды, ответы     desctop_app/protocol/client.py
         по номеру, очереди
               |
      Transport: строки в порт       transport.py  либо  emulator.py
               |
        USB Serial, 115200
               |
        ESP32 (esp32/src/main.cpp)
               |
      TTL half-duplex, 1 Мбод, GPIO 18 (RX) и 19 (TX)
               |
             STS3215
```

| Файл | Строк | Назначение |
|---|---|---|
| `protocol/message.py` | 147 | описание протокола, сборка и разбор сообщений |
| `protocol/transport.py` | 115 | порт: открыть, прочитать строку, записать, закрыть |
| `protocol/client.py` | 119 | поток чтения, ответы по номеру команды, очереди |
| `protocol/emulator.py` | 416 | эмулятор платы с моделью привода для демо-режима |
| `ui/main_window.py` | 545 | окно, панель, консоли, связь с устройством |
| `ui/home_tab.py`, `manual_tab.py`, `params_tab.py` | 660 | вкладки |
| `ui/widgets.py`, `params.py`, `theme.py` | 424 | общие виджеты, таблица параметров, тема |
| `esp32/src/main.cpp` | 700 | прошивка целиком |

**Асинхронность реализована через `threading`, а не `asyncio`.** Фоновый поток
читает порт, команды уходят своими короткоживущими потоками, результаты
возвращаются в интерфейс через очереди, которые разгребает таймер главного
потока. Причины отказа от `asyncio`: `pyserial` блокирующий и остановил бы
цикл событий; обёртка `pyserial-asyncio` (0.6, 2021) не заявляет поддержку
Windows, которая требуется по заданию; у Qt собственный цикл событий, и
совмещение потребовало бы прослойки. Подробнее в докстринге `client.py`.

## Протокол ПК и ESP32

Одно сообщение это одна строка JSON, разделитель `\n`. Полное описание с
полями, единицами и правилами лежит в докстринге
[`desctop_app/protocol/message.py`](desctop_app/protocol/message.py).

| Вид | Направление | Назначение |
|---|---|---|
| `cmd` | ПК в плату | команда, несёт `id` |
| `resp` | плата в ПК | результат, несёт тот же `id` |
| `tlm` | плата в ПК | телеметрия, без `id` |
| `evt` | плата в ПК | событие, без `id` |

Команды: `ping`, `get_config`, `set_config`, `move`, `motor`, `stop`, `home`.

```
-> {"type":"cmd","id":1,"cmd":"move","pos":3000}
<- {"type":"resp","id":1,"ok":true,"data":{"pos":3000}}
<- {"type":"tlm","t":12345,"pos":2950,"tgt":3000,"spd":850,"load":320,"cur":95}
<- {"type":"evt","event":"homing","status":"completed","zero":0,"zero_raw":486}
```

Телеметрия идёт 20 раз в секунду в движении и 5 раз в покое. Медленно
меняющиеся поля (напряжение, температура, режим, ошибки) повторяются раз в
десять кадров, поэтому обычный кадр занимает около 78 байт вместо 125.
Кадр телеметрии расходный: если буфер передачи полон, плата его пропускает,
а ответы на команды не пропускает никогда.

## Homing и меры безопасности

Поиск механического нуля выполняет **плата**, конечным автоматом, без
блокирующих ожиданий в главном цикле.

1. Привод переводится в режим постоянной скорости и едет в заданную сторону со
   скоростью поиска.
2. На каждом шаге проверяются нагрузка и ток. Упором считается **превышение
   порога три замера подряд** и не раньше чем через 200 мс после старта: на
   разгоне нагрузка скачет, и одиночный выброс это ещё не упор.
3. Найденная точка становится нулём. Система координат ведётся на плате:
   запоминается сырая позиция упора, и дальше все позиции протокола
   отсчитываются от неё. Пределы `min_pos` и `max_pos` пересчитываются и
   перезаписываются в сервопривод.
4. Отказы сообщаются событием с причиной: `timeout`, `travel_exceeded`,
   `servo_silent`, `host_timeout`.

Запись 128 в регистр 0x28 сознательно не используется: она жёстко назначает
текущей точке значение 2048, что бы ни стояло в настройке нулевой позиции, и
пишет смещение в EPROM, ресурс которого ограничен.

**Что останавливает привод:**

- **STOP** доступен всегда, в том числе посреди homing, и вынесен в постоянную
  панель, чтобы не зависеть от открытой вкладки. Обнуления скорости
  недостаточно: регистр цели при этом сохраняется, поэтому цель перебивается
  текущей позицией, а если сервопривод не ответил, снимается момент.
- **Выход за диапазон** в режиме непрерывного вращения. Сам сервопривод в этом
  режиме угловые пределы не соблюдает, поэтому за ними следит плата по
  телеметрии.
- **Молчание сервопривода** пять опросов подряд.
- **Потеря связи с ПК.** Плата питается отдельно и не узнает, что кабель
  выдернули, поэтому останавливает движение, если команд не было три секунды.
  Приложение, пока привод движется, подтверждает присутствие каждые полторы
  секунды.
- **Молчание платы.** Приложение следит за паузой в телеметрии и сообщает,
  если она длится дольше двух секунд.

Износ EPROM учитывается: в сервопривод записываются только изменившиеся
регистры, а режим работы пишется лишь при реальной смене.

## Известные ограничения

**Ничего не проверено на оборудовании.** Платы и сервопривода не было,
проверены только компиляция прошивки и полный сценарий в демо-режиме.
Требуют проверки на железе в первую очередь:

- поведение замка EPROM (регистр 0x37): на нём построена задумка настраивать
  коэффициенты регулятора без износа ячеек;
- код модели сервопривода: читается из регистров 0x03 и 0x04, но какое именно
  число возвращает STS3215, неизвестно;
- обрыв USB во время работы: виртуальный порт этот случай не воспроизводит;
- мусор загрузчика ESP32 при открытии порта: обработка написана вслепую.

**Точность сторожа диапазона** ограничена периодом опроса. При 20 Гц и
скорости 3400 шаг/с привод успевает проскочить границу до 170 шагов, это около
15 градусов.

**Конфигурация читается из памяти платы**, а не из регистров сервопривода.
Значит индикатор «значение на плате» показывает записанное нами, и разойтись с
реальным содержимым регистров они могут.

**Вкладка «Ручное управление» это заготовка:** графики и ползунки регулятора
расставлены, но команд настройки коэффициентов пока нет.

## Что дальше

1. Проверка на оборудовании по списку выше.
2. Настройка коэффициентов регулятора через замок 0x37.
3. Тесты протокола: `message.py` состоит из чистых функций и покрывается без
   железа.
4. Выгрузка телеметрии в CSV и логирование в файл.
5. Выделение слоя логики между интерфейсом и клиентом: сейчас связка живёт в
   окне, и при росте числа команд это станет тесно.
